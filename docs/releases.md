# Версии и выпуск

Единственный источник номера — `version` в `package.json`. Первый номер раннего
доступа — `0.1.0`. Используем обычные версии `MAJOR.MINOR.PATCH` по
[SemVer 2.0.0](https://semver.org/), без prerelease и build metadata.

До `1.0.0` исправления повышают PATCH, новые возможности и несовместимые
изменения — MINOR. `1.0.0` означает готовность поддерживать стабильный контракт.
После него несовместимые изменения повышают MAJOR, совместимые возможности —
MINOR, исправления — PATCH. Контракт включает HTTP API, WebSocket-сообщения,
вход и сохранённые пользовательские данные. Переименование надписей интерфейса
само по себе не меняет API; миграция должна сохранять существующие данные.

История живёт в `CHANGELOG.md`. У каждого опубликованного номера один коммит,
аннотированный Git-тег `vMAJOR.MINOR.PATCH` и Docker-образ
`<APP_IMAGE_REPOSITORY>:MAJOR.MINOR.PATCH`. Опубликованные теги
и образы не переписываем. SHA коммита передаётся в OCI label и `/version`
отдельно от номера. В профиле отображается версия, `/healthz` отдаёт её в
заголовке `X-App-Version`.

## Подготовка

В каноническом checkout на `main`:

1. Добавить описание изменений под `## [Unreleased]` в `CHANGELOG.md`.
2. Выбрать уровень и выполнить `bun run version:bump patch` (либо `minor`,
   `major`). `--dry-run` показывает будущий номер без записи. Команда обновляет
   manifest и переносит заметки в раздел нового релиза с датой.
3. Выполнить `bunx tsc --noEmit`, `bun test tests/version.test.ts` и проверки,
   необходимые для конкретных изменений. Проверить diff, закоммитить и
   отправить код в `origin main`.

## Публикация

```sh
# APP_IMAGE_REPOSITORY задаётся в локальной конфигурации, без тега.
bun run release:check
bun run release:tag
bun run release:build
```

Проверка требует зафиксированных manifest и истории текущего релиза и
отказывается использовать номер, уже закреплённый тегом за другим коммитом.
Повторный `release:tag` для того же коммита безопасен, в том числе после сбоя
push. `release:build` требует опубликованного тега и проверяет отсутствие
образа в registry; существующий образ не пересобирается. Если registry
недоступен, сборка останавливается.

Сборка через `docker buildx build --platform linux/amd64 --push` получает
архив конкретного коммита и только разрешённые файлы приложения. Изменения,
ещё не попавшие в коммит, в образ не входят. Builder выбирается окружением
машины. Для другого кода нужен следующий номер; `latest` не используем.

## Развёртывание

Развернуть опубликованный образ с номером без `v` средствами выбранного
окружения. Поддерживаются обычный контейнерный runtime и оркестратор;
конфигурация размещения и секретов определяется оператором установки.
Сверить `GET /version` (номер и SHA) с тегом и дождаться готовности приложения.
Откат использует уже опубликованный совместимый образ; существующие старые
SHA-теги остаются доступны. Совместимость миграций БД проверяется перед откатом
отдельно.
