# Изолировать документы и слайды по пользователю и проекту

## Контекст и задача

Нужны загрузка TXT/PDF/DOC, распознавание, векторный поиск в PostgreSQL и презентации с отдельными наборами документов. Дополнительная личная база знаний должна оставаться доступной только явно настроенному владельцу. Прежняя реализация имела одну общую комнату, сессию и OpenViking-источник: перенос такой модели на нескольких пользователей раскрывал бы документы, речь и слайды.

Связанный ADR: `docs/adr/0001-live-pipeline.md`; изучен конвейер режиссёра и независимых источников. Затронутый код: `src/server.ts`, `src/session.ts`, `src/sources.ts`, `src/knowledge.ts`, `src/auth.ts`, `migrations/001-projects.sql`, `migrations/002-account-profile.sql`. Репозиторий использует `docs/adr/` как каноническую директорию решений.

## Критерии выбора

1. Изоляция документов, фрагментов, слайдов, речи и событий WebSocket.
2. Серверная проверка личности для доступа к личной базе; отсутствие её ключа в браузере.
3. Собственный PostgreSQL и существующий private LiteLLM.
4. Загрузка документов без попадания в личный архив Paperless.
5. Фоновая обработка, сохранение очереди после перезапуска и понятные ошибки.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Загружать в Paperless и искать по его индексу | Готовый OCR, извлечение текста и управление документами | Нужна отдельная модель tenants; личный архив смешивается с продуктом, права двух систем требуют синхронизации |
| Загружать в OpenViking, отделяя ресурсы проектами | Используется готовый retrieval API | Основной индекс другой системы; запросом явно выбран PostgreSQL, риск смешения личных scopes |
| Хранить документы и pgvector-фрагменты в отдельной БД приложения, извлекать текст инструментами PDF/OCR и Tika | Контроль владения в одном месте, транзакционное состояние, не затрагивает архив | Очередь и статусы поддерживаем сами, OCR требует CPU и памяти |

Оставить общую комнату нельзя: это противоречит основному требованию приватности.

## Решение

Выбран третий вариант.

- PostgreSQL хранит проекты, исходные файлы, задания и фрагменты с `vector(1024)`. Поиск ограничен выбранным проектом и владельцем до ранжирования.
- У контентных таблиц включены `ENABLE` и `FORCE ROW LEVEL SECURITY`; runtime-роль не может быть superuser или BYPASSRLS. Идентификатор владельца задаётся через `set_config` внутри транзакции, а не на уровне общего пула.
- TXT читается как UTF-8; PDF извлекается через Poppler, страницы без текстового слоя распознаются Tesseract `rus+eng`; DOC — antiword; DOCX — существующий Tika, без импорта в Paperless.
- Обработка последовательная и имеет сохраняемые состояния `queued/processing/ready/error`, аренду задания и ограниченные попытки восстановления. Фрагменты становятся доступны поиску только после полного успешного индексирования.
- Embeddings: существующий алиас `openviking-embedding` private LiteLLM, 1024 измерения. Смена модели требует повторной индексации: фрагменты другой модели поиском не используются.
- Вход раннего доступа — аккаунты, созданные администратором. Пароли берутся из именованных `pass` entries, в БД остаётся Argon2id-хеш; cookie HttpOnly/SameSite=Strict/Secure на HTTPS, серверная сессия действует 12 часов.
- Аккаунты и сессии находятся в собственной БД сервиса `live_slides`. Дополнительный явный вход `/auth/corp` проверяет настоящую Corp-cookie через фиксированный `/auth/verify` и выдаёт cookie самого приложения. Обычные API/WebSocket проверяют только собственную сессию. В профиле можно задать/сменить логин и пароль; смена пароля отзывает все старые сессии. Создание пароля у владельца сохраняет его UUID и subject `corp:<owner>`, поэтому личный источник остаётся доступным; отдельный `local:<owner>` таких прав не имеет. Клиентские заголовки личности не принимаются.
- Личная база подключается по внутреннему OpenViking API сервером с ключом из `pass`/Kubernetes Secret. URL, ключ, scopes и содержимое не возвращаются чужим аккаунтам. По умолчанию проект использует только свои документы; включение личной базы делается при создании проекта владельцем.
- Сессии, кеши и WebSocket разделены по `user_id:project_id`, файлы — по `data/users/<user>/projects/<project>/sessions/`. Прежние общие сессии автоматически не присваиваются пользователям.

## Последствия

Положительные: проверка владения работает и в API, и в БД; приватный архив не меняется; ошибки извлечения и embeddings не публикуют частично готовый индекс. Модель существующего режиссёра сохраняется, а новый источник реализует его обычный интерфейс.

Отрицательные: исходники в bytea увеличивают объём БД и бэкапов; точный поиск растёт с количеством фрагментов; один worker ограничивает пропускную способность. OCR может ошибаться и расходует CPU; embeddings и облачный LLM проходят через шлюз к его провайдеру, что не означает полностью локальную обработку текста. Нужны лимиты и контроль очереди.

Лимиты раннего доступа: файл 20 МБ, PDF 60 страниц, распознанный текст 1 млн символов; аккаунт 200 МБ исходников, 200 документов и 50 проектов. Удаление документов, совместный доступ и самостоятельная регистрация пока не входят в интерфейс.

## Проверка

- Интеграционные тесты на настоящем PostgreSQL/pgvector с ролью без привилегий обхода RLS.
- Два аккаунта: прямой запрос чужих проектов/документов/колоды, подстановка заголовка личности, подписка и события WebSocket, прекращение доступа после выхода.
- Успешный retrieval из своего проекта и отсутствие результатов из чужого; запрет включения личного источника обычным аккаунтом, включая прямую запись в БД под tenant-контекстом.
- Восстановление задания после истечения аренды, атомарность неуспешного индексирования и повторная обработка.
- Реальные синтетические TXT, PDF с текстом, скан PDF на русском, DOC/DOCX; проверка интерфейса на desktop/mobile и первого слайда демонстрации без JavaScript.

Источники API: [Bun SQL](https://bun.sh/docs/runtime/sql), [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [pgvector](https://github.com/pgvector/pgvector), [Tika Server](https://cwiki.apache.org/confluence/spaces/TIKA/pages/148639291/TikaServer).
